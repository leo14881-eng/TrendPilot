## 1. 目标与边界

**目标**：用 Java 重建旧影子交易系统的主链，第一期先跑通最核心的一条线：

行情 → EARLY 候选 → Capital Review → V2 影子账本 → 5 分钟持仓管理 → Telegram 通知。

**硬边界（第一天就写进代码和测试）**

- 只做影子模拟。不引入任何交易所下单 API，`capital_authority` 固定为 `NONE_SHADOW_ONLY`，用 ArchUnit 测试禁止依赖下单类。
- 策略参数不自动优化，只能人工修改配置文件。
- 数据不完整时宁可停、宁可拒绝，绝不伪造价格、深度或成功状态（沿用旧系统第十一节全部原则）。

## 2. 第一期总体形态：一个服务

```
本机 Windows
└─ trendpilot.jar（一个 Java 进程，java -jar 启动）
    ├─ 内置定时任务（Discovery 每小时 / Monitor 每 5 分钟）
    ├─ Binance REST 行情客户端
    ├─ 策略规则（纯函数）
    ├─ SQLite 数据库文件 data/trendpilot.db（账本、运行记录）
    ├─ Telegram 机器人通知
    └─ 本地只读网页 http://localhost:8080（查看持仓和最近决策，可选）
```

- 只有一个进程、一个数据库文件、一个配置文件。不需要安装数据库、Docker 或其他服务。
- 只运行一个实例，组合写入用进程内锁即可，不再需要 Git CAS、跨环境锁或 GitHub Actions 备用路径。
- 本机关机或休眠时系统停止；重启后先做一次完整性检查再继续（见 5.6）。

## 4. 包结构

```
com.trendpilot
├─ common        Money、Bps、Generation、结果码、时间截面
├─ market        Binance REST 客户端、K 线/盘口快照、完整性检查
├─ universe      标的过滤（USDT 现货、排除稳定币/法币/代币化股票）
├─ signal        EARLY 六条件与评分
├─ capital       Capital Review、RR 成本情景模型、资金队列
├─ portfolio     V2 影子账本（事件表 + 持仓视图）、加仓规则
├─ monitor       退出顺序、利润保护、LOSS_RECOVERY
├─ risk          系统风险（BTC + 市场广度）、亏损冻结
├─ notify        Telegram 发送、Outbox、去重
├─ job           DiscoveryJob、MonitorJob、启动自检
└─ web           只读状态页（可选）
```

**原则**：信号、审核、退出全部写成纯函数：输入一个冻结的数据截面，输出决策和理由码。这样实时运行、单元测试、和旧系统对拍都用同一份代码。

## 5. 第一期关键设计

### 5.1 行情（第一期只用 REST）

- 第一期只接 **Binance**，只用 **REST**：exchangeInfo、24h 行情、15m/1h/1d K 线、BTC 5m、盘口深度。
- 理由：Discovery 每小时一次、Monitor 每 5 分钟一次，REST 完全够用；WebSocket 的订阅确认、epoch、缺口、断线补数是旧系统最复杂的部分，放到第二期。
- 每轮抓取生成一个 **generation**（编号 + 时间截面），一轮内所有决策只读这个截面。
- 并发最多 4 个请求，遵守 Binance 权重限制，有界重试 + 指数退避。
- 数据不完整：记录缺失名单，标 `PARTIAL_DATA`；BTC 基准缺失则本轮不出信号；持仓必需价格缺失则 Monitor 本轮停止。

### 5.2 EARLY 信号

按旧系统第四节实现六条件（至少命中两条）和评分；1h/4h 收益沿用旧实现「2/5 根小时 K 线首开至末收」，保证对拍一致。20%/8% 涨幅只做标签。

### 5.3 Capital Review 与资金

- 规则按旧系统第六、七节一比一实现：score≥8、1h 相对 BTC≥0.8 或 4h≥1.5、信号和盘口一小时内、价差≤50bps、±2% 两侧深度≥30,000U、模拟滑点≤75bps、RR≥1.5（高于首次 EARLY 价 12% 以上 RR≥2，24h 涨超 20% 加严）。
- 身份核验第一期简化为：Binance 官方标的 + 本地黑名单/人工确认名单；没有解锁数据时记为「研究缺口」，**不当作硬拒绝也不当作通过的理由**，在决策理由中写明。
- V2：20,000U 硬顶（普通 17,000U + 储备 3,000U），每笔 1,000U，每币最多 3 笔；市场状态部署上限 60/75/85/95%；BUY 与 ADD 同队列竞争预算。
- 所有阈值放在 `config/strategy-params.yml`，每条决策记录所用参数版本。

### 5.4 Monitor 退出

按旧系统顺序：硬失效 → 持久利润保护 → 普通论点失效（亏损进入 LOSS_RECOVERY）→ 8% 复核 → 继续持有。

- 利润保护：原始收益≥2% 且新鲜盘口净利>0 启动；底线 = max(本金 0.35%, 最高可退出净利 − 本金 2%)，只上调，加仓后重设基准；跳空穿透只记录、不亏损卖出。
- 普通衰退：至少两项弱条件、连续三个有效观察代次。
- **改进**：所有退出统一用全数量盘口模拟成交，不再用「参考价 + 费用模型」。

### 5.5 账本与持久化

- `shadow_event` 表只追加（BUY/ADD/SELL/PROTECT_ARM…），持仓和资金池由事件计算。
- 每次运行写 `job_run` 表：开始/结束时间、generation、结果码；「程序成功」和「数据完整」分两个字段。
- 每天自动备份一次 SQLite 文件到 `backup/`。

### 5.6 调度与本机运行（越南时间）

| 任务 | 时间 |
|---|---|
| Discovery → Capital Review | 每小时 :17 |
| Monitor | 每 5 分钟 |
| 自检（替代 Watchdog） | 每小时 :37，异常时发 Telegram |

- 启动时自检：检查上次运行时间，若错过的 Monitor 超过 15 分钟，先发 Telegram 提醒「系统曾中断」，再用最新数据跑一次 Monitor；**不补造中断期间的交易**。
- 提供 `start.bat`，可选注册为 Windows 开机自启。

### 5.7 Telegram 通知

- 内容：影子 BUY/ADD/SELL、利润保护触发、系统风险变化、任务异常、每日汇总。
- 先写 Outbox 表再发送，状态 `PREPARED → SENT → FAILED`，按事件 ID 去重，失败重试。
- 需要你提供：Bot Token 和 Chat ID（放在本机配置文件，不进代码仓库）。
- 手机指令（只回应配置的 Chat ID，只由持有运行权的那台机器回应，长轮询 getUpdates 每约 25 秒一次请求）：
  - `/holdings`（或 `/v2`）：当前持仓、当天盈亏和资金情况，与 `/api/holdings` 同一份内容。
  - `/status`：程序版本、策略版本、运行机器、最近一次成功的持仓检查、各账本持仓数；某一项取不到时写"暂时取不到"。
  - `/help`：指令列表。服务部署在云服务器上、8080 端口不对外开放时，用这几个指令代替网页接口查看。

## 7. 验收

1. **单元测试**：每条规则用旧系统说明中的阈值写边界用例。
2. **对拍**：新系统在本机跑一到两周，与旧系统同时段的 EARLY 名单、审核结论、影子事件逐条比较，差异逐条归因（第一期只比较 Binance 部分）。
3. **验收标准**：
   - 能跑：本机连续 7 天无人工干预运行，Telegram 通知正常。
   - 第一期通过：对拍差异全部有解释。
   - 策略是否盈利：只看长期影子账本，系统本身不承诺。

## 9. MVP 和完整版的区别

**MVP**（最小可用版本）就是第 2–8 节描述的第一期：先用最少的功能把主链跑通，能在本机每天自动运行、发 Telegram 通知、和旧系统对拍。**完整版**是把旧系统的所有功能都搬过来。两者都是单服务、本机运行。

| 功能 | MVP（第一期） | 完整版 |
|---|---|---|
| 交易所 | 只有 Binance | Binance + Bybit 独立池 |
| 行情获取 | REST 定时拉取 | WebSocket 实时缓存 + REST 补缺 |
| FastWatch 快速观察 | 无 | 有 |
| EARLY 信号与评分 | 有 | 有 |
| 研究 | 简化：官方标的 + 黑名单，缺资料记为研究缺口 | 完整：CoinGecko、DefiLlama、解锁、供给、价值捕获 |
| Capital Review 买入审核 | 有（全部阈值） | 有 |
| V2 影子账本、资金池、加仓 | 有 | 有 |
| V1 宽口径观察账本 | 无 | 有 |
| 5 分钟持仓管理、利润保护、8% 复核 | 有 | 有 |
| 系统风险 | 简化：BTC + 市场广度 | 完整：再加流动性、稳定币证据 |
| 再入场规则 | 基础版 | 完整版 |
| Blind / Missed Replay 复盘 | 无 | 有 |
| Telegram 通知 | 有 | 有 |
| 工期（1 人） | 约 7 周 + 1–2 周运行观察 | 约 4 个月 |

**建议先做 MVP**：7 周后就能在本机看到系统真实运行、收到通知，和旧系统对拍发现问题后再决定第二期优先做哪些功能；MVP 的代码完整版会直接沿用，不会白做。

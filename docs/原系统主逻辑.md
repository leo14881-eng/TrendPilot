# 原系统主逻辑（用户提供，2026-10-14）

> 原样保存，作为重写的业务依据。基线：btc-grid-state ad63426。

下面是当前币圈影子系统的完整主逻辑，包含 WebSocket。已按最新 main 代码核对，基线为 ad6342691a9ba9ce111d832c770c47373587be5a，时间为2026年10月14日越南时间20:14左右。
先说最重要的结论：目前是“行情发现＋研究审核＋影子资金组合＋定时管理”的系统。WebSocket基础代码已经存在，但正式 Research／Monitor 尚未全部切到 WebSocket缓存；新并发优化仍在候选PR中。
一、整条业务链
行情全集 → EARLY候选 → 身份、研究和流动性检查 → Capital Review → V1／V2影子账本 → 五分钟持仓管理 → 持久化并回读main → 独立交易通知。
所有BUY／ADD／SELL都是模拟事件。真实交易关闭，capital_authority为NONE_SHADOW_ONLY。策略优化器当前冻结，不会自动改参数。
二、行情从哪里来、扫描哪些币

* Binance：官方exchangeInfo和24小时行情，选择正在交易、允许现货、USDT计价的标的。
* Bybit：官方现货instruments和tickers。
* 排除配置中的稳定币、法币以及官方代币化股票。
* Universe本身没有最低市值、最低成交额或固定币数门槛，但价格和成交额必须有效。
* 同ticker优先使用Binance参考价，不代表已经确认跨交易所合约身份一致。
* Bybit-only信号使用Bybit自己的BTC基准，基准缺失时不能拿Binance顶替。

24小时涨幅20%、8%等分类只是研究标签，不直接触发买入。
三、WebSocket在系统中的位置
目前有两套用途不同的WebSocket。
1）FastWatch快速观察

* Binance订阅bookTicker和aggTrade。
* Bybit订阅现货orderbook.1。
* 快速观察价格、价差和假设利润保护，REST用于备用及核对。
* formal_writer=false，只写观察结果，不写正式组合，也不会直接产生正式SELL。

所以，即使FastWatch发现卖出条件，正式组合仍要走权威持仓管理链路。
2）K线缓存采集器

* Binance订阅扫描范围的15m、1h、1d，加BTC的5m。
* Bybit订阅指定范围及BTC的15m、60m。
* 数据进入各自SQLite，消费者按同一时间截面读取冻结generation。
* 不是每来一条WebSocket消息就执行买卖。

3）缓存可用的条件
必须检查订阅确认、连接epoch、来源与标的范围、K线连续性、缺口、generation、证明和哈希。相关新鲜度窗口为90秒，读取结束还会复查。过期或不完整就拒绝使用。
4）断线与补数
REST负责初始化和补缺；重连成功不等于数据已经READY。Binance有分片、最多4个REST并发、有界恢复与指数退避；Bybit也有订阅分批、有限重试和跨进程共享冷却。不能靠无限重试或重启清掉拒绝状态。
5）当前实际接线

* Binance K线来源默认仍是REST，显式选择SPOT_CACHE才读取缓存；缓存失败不偷偷退回REST。
* Research的EARLY入口已有缓存接线。
* 当前Monitor的持仓1h／4h／15m信号仍直接走REST；Bybit持仓管理K线同样如此。
* Monitor里的BTC 5m系统风险窗口可间接受缓存selector控制。
* 最近实际Bybit扫描产物仍标明VIA_WORKER，不能说已经切到缓存。

四、怎样进入EARLY候选
六个条件至少命中两个：

* 1h相对BTC收益≥0.8个百分点
* 4h相对BTC收益≥1.5个百分点
* 相对收益加速度≥0.5个百分点
* 15分钟成交额加速比≥1.35
* 区间压缩比≥1.2
* 最近15分钟动量非负，同时1h相对BTC≥0.25个百分点

然后按相对强度、加速度、量能和压缩程度评分。EARLY不要求分数达到8，分数8是后面V2买入审核的门槛。
这里有个实现细节：代码里的“1h／4h”收益使用2／5根小时K线的首开至末收，并非严格两个墙钟时点之间的收益。
[信号公式](https://github.com/leo14881-eng/btc-grid-state/blob/ad6342691a9ba9ce111d832c770c47373587be5a/research/hunter_early_signals.py#L26-L188)
五、研究阶段干什么
每轮默认轮转研究25个币，再加入前10个EARLY和前10个价格异动币。读取CoinGecko、DefiLlama、日K和官方资料，检查身份、供给、解锁、价值捕获及证据缺口。
长期研究本身不会直接给买单：Forward Research的capital_ready始终为false，长期估值资料齐全后也可以只是USER_REVIEW_REQUIRED。
战术买入另走Capital Review。基本面资料不全多数记为研究缺口；明确重大近期解锁、身份错误等才是相应硬拒绝。不能把“资料还没全”当成所有不买的统一解释。
六、V2真正买入还要过哪些门
Capital Review按SYSTEM_BLOCKED、REJECT、WAIT、BUY分类。只有最终BUY才有资格分配资金。
主要条件：

* 扫描、身份、流动性和信号代次一致，关键数据完整
* 身份核验通过，执行渠道支持，无明确重大近期解锁
* EARLY至少两个独立条件，score≥8
* 1h相对BTC≥0.8或4h≥1.5
* 信号和盘口在一小时内
* 价差≤50bps，即0.5%
* 价格上下2%范围内，买卖两侧深度各≥30,000U
* 模拟买入滑点≤75bps，即0.75%
* 情景收益风险比RR≥1.5
* 首次发现价、追涨限制及资金审核通过

高于首次EARLY价超过12%，RR要求提高到2；24小时已涨超过20%，还要求更强的相对收益和正加速度。
RR来自成本情景模型，不是预测收益：其中假设跌2.5%是风险测算，不是自动止损线。
[完整买入门槛](https://github.com/leo14881-eng/btc-grid-state/blob/ad6342691a9ba9ce111d832c770c47373587be5a/research/hunter_tactical_capital_review.py#L38-L139)
七、V1、V2和加仓
V1是宽口径观察样本，EARLY至少两个信号即可进入相应判断，没有V2那样的组合资金池与数量上限，但仍受明确身份错误、渠道和系统风险等限制。不能把V1的样本收益直接当作可执行组合收益。
V2固定20,000U硬上限：普通机会17,000U，战略储备3,000U；每笔1,000U，每币最多三笔、合计3,000U。
加仓不是跌了就补，必须：

* 持仓健康为STRONG，重新通过审核
* 当前价低于上一笔，并达到按波动和交易成本计算的最低降价幅度
* 第三笔要求更大的降价幅度
* 新信号ID、新generation、新盘口及恢复确认
* 信号至少间隔15分钟
* 资金允许

BUY与ADD一起排序争取预算。V2 Monitor只生成ADD候选，交回资金队列，不能绕过资金审核。
市场状态限制可部署比例：RISK_OFF为60%，NEUTRAL为75%，CONSTRUCTIVE为85%，STRONG为95%；还受现金底、亏损隔离与20,000U硬顶约束。浮盈不会自动扩大资金池，资金不足就等待，不为了腾资金机械卖亏损仓。
八、五分钟Monitor怎样决定卖出
当前退出顺序是：
1）硬失效：明确身份、合约、供给问题，或严重流动性异常等，允许亏损退出。
2）持久利润保护触发，且全数量模拟退出仍有净利润。
3）普通论点失效：有净利润可退出；亏损时进入LOSS_RECOVERY观察。
4）原始收益达到8%时复核：相对强度和加速度仍好就继续持有，否则走退出。
5）其他情况继续持有。
普通健康衰退要求至少两项弱条件，并连续三个有效观察代次；掉出候选榜本身不等于失效。
因此，当前没有固定百分比止损，也没有持有X小时强制退出。“亏损＋信号普通变弱”可能继续持有，这就是现有策略行为，不能理解成一定是系统卡住。
九、2%保护与8%复核的准确含义
当前main仍有这些参数：

* 原始收益≥2%，且新鲜盘口估计净利润>0，才启动利润保护。
* 净保护底线取“本金0.35%”与“最高可退出净利润减本金2%”的较高值。
* 底线只上调，加仓后重新基准化。
* 当前可退出净利润跌到保护底线以下、但仍大于0，才触发保护SELL。
* 如果跳空后已经没有净利润，记录穿透保护窗口，不自动亏损卖出。
* 8%只是再次检查是否继续持有。

注意一个现有实现限制：利润保护与Bybit退出检查全数量盘口；部分Binance退出仍使用参考价加费用模型。不能宣称所有影子成交都已经模拟了完整真实成交条件。

十、系统风险、亏损恢复与再入场

* 系统风险结合BTC、市场广度、流动性和稳定币证据；关键数据缺失时保守限制新BUY／ADD。
* 亏损冻结同时考虑已发生的亏损退出和确认的市场冲击，不能仅凭缺数据就假装发生了市场冲击。
* 风险解除需要多次独立正常观察，额度分阶段恢复。
* 再入场要求退出后的新鲜、独立、有序证据，重新通过BUY和资金审核；不是刚卖掉立刻按旧信号买回来。
* 旧配置里的固定3%回撤／1%突破，不是当前实际再入场函数采用的通用条件。

十一、数据不完整时怎么处理

* Binance扫描不完整：不推进正常下游基线。
* Bybit局部缺K线：保留缺失名单，标PARTIAL_DATA，不伪装成全量成功。
* Bybit BTC基准缺失：该独立池不能计算信号。
* 持仓必需价格缺失：Monitor停止本轮。
* 退出盘口失败：清空这份盘口，不复用旧深度假装新鲜。
* 新买入缺关键证据：阻止买入。
* 系统风险资料不全：限制新增风险，不凭空构造卖出价格。

程序SUCCESS只代表程序执行完成，不代表所有币都有合格数据。
十二、谁负责写账本，什么时候运行
当前配置：

* Discovery每小时越南时间:17，成功后启动Research
* Monitor每5分钟
* Watchdog每小时:07和:37
* Blind Replay每小时:31
* Missed Replay每天越南时间23:55

Research与Monitor共享本机组合锁；GitHub端有并发限制，跨环境还靠Git CAS检测冲突。这不是一个已经完全统一的跨平台租约系统。
Research的组合临界区限90秒。Monitor先验证产物，再push，最后实际读取main核对。发生冲突要重新取最新状态、重新计算，不能直接重推旧JSON。GitHub Actions保留备用路径，有合格服务器成功证明才正常跳过。

十三、其他模块不参与直接买卖

* Watchdog：检查任务是否及时、代次是否衔接；发现异常不等于恢复已经成功。
* Blind Replay：历史规则与样本外研究，当前覆盖有限，不能当作策略盈利已经证明。
* Missed Replay：复盘涨幅榜、何时发现、为何未买，不补造历史交易。
* 通知消费者：读取V2正式事件并去重；PREPARED只表示准备，不能当作用户已收到。
* Sentinel：正式writer仍是ChatGPT自动任务，服务器保持preview边界，完整分析迁移尚不能算完成。

十四、现在完成到哪里
主链Discovery、Research、Monitor、持久化和回读已经有实际成功记录。但完整WebSocket缓存消费、新控制协调和WAL性能优化不能算全部上线；PR131／136等仍未合并，严格压力验收仍有队列满问题。
另外，Bybit的403数据缺口、Research接近90秒期限、通知送达回执等问题仍需分别核验。股票币圈能运行，与这套系统已经全面验收、策略已经证明盈利，是三个不同的完成标准。

# LP 影子盘方案（TrendPilot 新模块 `lpshadow`）

> 交给 Claude Code 实现。遵守 TrendPilot 全部现有规则：**SHADOW ONLY**、只用免费 API、SQLite、缺数据只能导致"不动作"、commit 后走 `./scripts/ship.sh`、commit 信息用正面描述（会原样推送到 Telegram）。

## 1. 目标

用**链上实时数据**验证"Uniswap V3 集中流动性做市 + 合约对冲"能不能在扣掉所有成本后稳定跑赢基准。跑 **60 天**，到期按第 8 节的标准给出"做 / 不做"的结论。

背景：离线回测（`docs/回测报告/lp_backtest.py`，过去一年 ETH 小时价 + DefiLlama 每日手续费）显示：
- 不对冲：在 0.05% 池子全部跑输持有 50/50；
- 对冲后：结果从 −60% 到 +120%，**完全取决于同池其他 LP 的集中度（竞争强度 m_avg）**，这个变量离线无法测出。

影子盘的核心价值是**用 feeGrowthGlobal 直接测出我们这个区间真实能分到的手续费**，消掉这个未知数。

## 2. 硬约束

- 纯只读：只做 `eth_call` 和公开行情查询。**不创建钱包、不碰私钥、不签名、不发交易。**
- 免费公共 RPC：Base `https://mainnet.base.org`、Arbitrum `https://arb1.arbitrum.io/rpc`。用 JSON-RPC batch 请求，每条链配一个限流器，遇到 429 退避。
- 缺数据（RPC 超时、价格缺失）：该时段标记为 `gap`，不计手续费、不调仓、不对冲，并在报告里写明覆盖率。
- 不依赖任何旧项目。

## 3. 跟踪的池子

| 链 | 交易对 | 费率 |
|---|---|---|
| Base | WETH/USDC | 0.3% |
| Base | WETH/USDC | 0.05% |
| Arbitrum | WETH/USDC | 0.05% |

**池子地址不要硬编码**，启动时用 Uniswap V3 Factory 的 `getPool(token0, token1, fee)` 解析，并校验两个 token 的 `symbol()` 和 `decimals()`：

- Base：Factory `0x33128a8fC17869897dcE68Ed026d694621f6FDfD`，WETH `0x4200000000000000000000000000000000000006`，USDC `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`
- Arbitrum：Factory `0x1F98431c8aD98523631AE4a59f267346ea31F984`，WETH `0x82aF49447D8a07e3bd95BD0d56f35241523fBab1`，USDC `0xaf88d065e77c8cC2239327C5EDb3A432268e5831`

以上地址实现时先用链上调用核对一次，任何校验不通过就停止该池并告警。

## 4. 数据采集（每 60 秒一次）

每个池子用一个 batch 读取：
- `slot0()`：sqrtPriceX96、tick
- `liquidity()`：当前活跃流动性 L_active
- `feeGrowthGlobal0X128()`、`feeGrowthGlobal1X128()`
- `eth_gasPrice`（按链）

另外从 Binance 合约公开接口读取 `ETHUSDT` 的 `premiumIndex`（标记价格、资金费率），用于对冲模拟。

写入表 `lp_pool_snapshot(ts, pool, sqrt_price_x96, tick, liquidity, fg0, fg1, gas_price_wei, perp_mark, funding_rate, status)`。

注意：feeGrowth 是 **uint256 且会溢出回绕**，差值要用 `BigInteger` 按 mod 2^256 计算。

## 5. 虚拟仓位与手续费计算

每个策略持有一个虚拟仓位：`(pool, tickLower, tickUpper, L)`，初始本金 **10,000 USDC**。

**手续费（每个采样间隔）**：
- 区间开始和结束时 tick 都在 `[tickLower, tickUpper)` 内：
  `fee0 = L × Δfg0 / 2^128 × L_active / (L_active + L)`，fee1 同理；
- 只有一端在区间内：按一半计；
- 都不在：不计。

最后统一换算成 USDC 计入，手续费单独累计，不复投。

**仓位价值**：用标准 V3 公式由当前价格算出 token0/token1 数量（区间下方全是 ETH，上方全是 USDC）。

**调仓（价格出区间时）**：
- 以当前价格为中心重开同宽度区间；
- 成本 = gas（实时 gasPrice × 400,000 gas × ETH 价格）+ 一半仓位价值 ×（池子费率 + 0.02% 滑点）；
- 可选冷却期参数：出区间后等 N 分钟仍未回到区间才调仓（默认 0，另跑一组 30 分钟作对照）。

**对冲（hedged 策略）**：
- 用 ETHUSDT 永续空单，数量等于仓位里的 ETH 数量；
- 偏离超过仓位价值 2% 时调整，手续费按 taker 0.05%；
- 每 8 小时按真实资金费率结算（空单在费率为正时收、为负时付）；
- 保证金按 3 倍杠杆占用资金，占用部分**不参与做市**，收益率按"做市本金 + 保证金"合计计算；
- 记录离强平价的距离，跌破 15% 记一次"爆仓风险事件"。

## 6. 策略矩阵

每个池子都跑：
- 区间宽度：±2%、±5%、±10%、±20%、±50%
- 不对冲 / 对冲
- 调仓冷却：0 / 30 分钟

共 3 × 5 × 2 × 2 = 60 个虚拟仓位。

**基准**（同起点、同本金）：
- 持有 50/50 ETH+USDC
- 只持有 USDC
- 只持有 ETH

## 7. 存储与报告

**表结构**
- `lp_position(id, strategy, pool, tick_lower, tick_upper, liquidity, opened_ts, closed_ts)`
- `lp_event(ts, strategy, type, detail_json)`：调仓、对冲调整、资金费结算、gap、爆仓风险
- `lp_daily(date, strategy, value, fees, il, gas_cost, swap_cost, hedge_pnl, funding, coverage)`

**每日报告**：`data/reports/lp-daily-<date>.md`，00:00（越南时间）生成。内容：
- 各策略累计净收益和年化，与三个基准对比
- 手续费、无常损失、各项成本、资金费的拆分
- 数据覆盖率

Telegram 每天推送一行汇总：最好和最差的 3 个策略，以及持有 50/50 基准。

**诊断指标**：每个池子每天计算实测集中度 `m_avg = L_active × 2√P / TVL`（TVL 由两个 token 的 `balanceOf(pool)` 得出），和离线回测假设的 5、10、20 对照。

**每周报告**：放 `docs/回测报告/`。对每个策略的日收益做 bootstrap，给出均值和 95% 置信区间，加上最大回撤和最长回撤。

## 8. 60 天后的决策标准

某个策略同时满足以下全部条件，才算"可以小资金实盘"：
1. 扣除全部成本和资金费后，年化净收益比只持有 USDC 高 **5 个百分点以上**；
2. 日收益 95% 置信区间下限 > 0；
3. 最大回撤 < 10%，且没有爆仓风险事件；
4. 在**至少 2 个池子**都成立（防止只是单个池子运气好）；
5. 数据覆盖率 > 95%。

达不到就写结论"不做"并停掉模块。是否实盘由我决定，模块本身永远不下单。

## 9. 测试（必须有）

- 仓位价值在区间边界连续（下沿、上沿两侧误差 < 0.01%）；
- 全区间无常损失符合理论值 `2√r / (1 + r)`；
- feeGrowth 溢出回绕：构造跨越 2^256 的差值，结果正确；
- tick 与价格互转，注意 USDC 6 位、WETH 18 位精度；
- 回放测试：用一段录制好的 snapshot 数据，结果和预先算好的数值一致；
- gap 处理：中间缺一段数据时不计费、不调仓。

## 10. 交付顺序

1. 数据采集 + 建表 + 池子地址校验，先跑 24 小时确认覆盖率；
2. 虚拟仓位和手续费计算（含测试）；
3. 调仓、对冲、资金费；
4. 每日、每周报告和 Telegram 推送；
5. 把 `lp_backtest.py` 和本方案放进 `docs/回测报告/` 归档。

每完成一步都走 `./scripts/ship.sh`，commit 信息示例："新增 LP 影子盘数据采集，覆盖 Base 和 Arbitrum 三个池子"。

## 成本口径调整（2026-10-30，用户批准："要，按实际成本来"）

方案第 5 节写的调仓 gas 是"实时 gasPrice × 400,000 gas × ETH 价格"。上线后发现 `eth_gasPrice` 在 L2 上只是 **L2 执行费**，不含把交易数据发布到以太坊主网的 **L1 数据费**（Base 上通常是调仓链上成本的大头），而且 40 万 gas 少于一次调仓实际的 decreaseLiquidity + collect + swap + mint。现在改为：

- L2 执行费 = gasPrice × 600,000 gas；
- L1 数据费：每分钟用 eth_call 读预部署合约估算（Base：GasPriceOracle `getL1FeeUpperBound`；Arbitrum：ArbGasInfo `getPricesInWei`），一次调仓按 3 笔 × 1,000 字节；
- 缺数据时沿用 1 小时内最近一次有效值，超过 1 小时该分钟不调仓。

改动前几个小时的虚拟仓位数据已清空，60 个仓位和 3 个基准按新口径在同一分钟重新开始，原始快照保留。新的起点和 60 天到期日见 docs/策略变更记录.md。
